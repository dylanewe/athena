# Exceptional environment-file access (#7)

Folder consent and ordinary Send do **not** approve actual environment files. An investigator's denied `.env` / `.envrc` read (including filename variants) offers the eligible filename, designated folder and reason in **Environment-file permissions**. Eligibility is established using path/stat checks, never by reading contents. Direct reads wait for a user choice within the existing job deadline. Listings can offer choices without reading the files. No agent tool can approve permissions.

- **Approve local inspection** reads a bounded preview into owning-window memory only. The preview is explicitly **Ephemeral · Local only · Not saved**. The investigator remains denied and waiting; local permission does not enter model context. Choose **Continue without this file** to continue with the denial.
- **Approve external processing** separately authorizes read-only processing of this exact file by the job's pinned investigator and main models. It does not imply local-preview permission or change route, provider, model, endpoint approvals, request limits, cost reservations or billing consent. On API-key routes, the two pinned role destinations may differ; approval covers both roles, not arbitrary external destinations.
- **Revoke and stop investigation** stops the whole affected job and its utility process, including pending reads and subsequent model sends. Data already transmitted to a provider cannot be recalled by Athena; incurred usage may remain. Cancellation cannot undo an OS operation already pending, but late content is not released.

Permissions are memory-only, scoped to the active investigation and exact folder-relative file. They expire on completion, failure, cancellation, wall-clock/request limits, close, quit and restart. The UI removes previews and permission controls on expiration. Stale approval IDs fail closed. Another job must request new approval. Neither source exceptions nor repository-discovery includes can grant environment access. The ordinary local Sources browser still cannot open actual environment files outside this investigation flow.

## Filesystem and secret boundaries

Approvals never bypass designated-folder consent, canonical path checks, symlink rejection (including ancestor symlinks), credential/Git ancestor protections, regular-file/encoding/size/range/output limits or cancellation checks. An exact approved environment read may pass default hidden/ignore exclusions for that file, never siblings. It does not turn search or directory traversal into environment-content access. Other credential-bearing file types remain denied. Recognizable examples/templates, including `.env.local.template` and `.envrc.local.template`, follow ordinary eligible-file rules and full-file secret checks; they do not require actual-environment approval and are not exempt from content checks.

Main continues to secret-check ordinary files before releasing excerpts. The worker records only the exact approved excerpts/assignment values in a memory-only final-request guard shared by both agent roles and transports. This permits the specifically approved content to pass the final secret guard, not arbitrary secret-bearing source files. Provider/network/protocol/byte/cost checks remain in force. The guard may conservatively reject complex transformations or secret-looking findings; approval is not permission to bypass all secret checks.

## Conservative persistence policy

**Before** releasing approved actual-environment content, main commits a safe ephemeral marker and seals the conversation. Failure to commit means no outbound permission and no content release. After sealing:

- All subsequent derived text, tool results, histories/reasoning signatures, exploration checkpoints, evidence/citations, candidate knowledge changes and titles stay out of SQLite, including WAL/SHM paths. Save retries go through the same storage guard; unsaved terminal data remains memory-only. The completed main history is not reusable; there is no cached-evidence or knowledge-excerpt write from this job.
- Public answer text may stream to the owning window from memory, visibly **Ephemeral · Not saved · May contain sensitive values**. Even innocuous paraphrases are not persisted. This is whole-context withholding, not a claim that a model cannot echo, encode or paraphrase secrets.
- Only a fixed safe placeholder and validated numeric usage/status metadata persist. Restart recovers that placeholder, not sensitive progress or worker context. Pending terminal-save retries cannot bypass the storage guard; display-only output remains in memory.
- Follow-up Send and Retry on that conversation are blocked before user-message persistence. Start a new conversation for fresh work. The renderer clears unsent drafts when sealing is observed. No worker, tool-result context or compaction summary is reused across investigations. There is no compaction. #8 adds a separate [knowledge database](knowledge.md), which excludes all exposed/tainted jobs from publication and reuse.

Ordinary, unapproved derived output is also secret-checked before any progress, title/history/evidence or exploration persistence. A suspected result switches the attempt to whole-output withholding and seals the conversation. Values recognized from local previews and outbound excerpts are remembered **only in memory** as a conservative session-level denylist for user prompts and derived persistence, never as authority to read/send another file. This compares text, not boolean/numeric control metadata. Low-information numeric/boolean/null-like scalar values are not denylist secrets in isolation; their full assignment/file text remains guarded. It can still withhold innocuous matching text. It is not a general paraphrase detector. Do not copy previews into other messages; after restart there is no persisted secret-value dictionary. Existing source/secret checks still apply.

The renderer is text-only and sandboxed. Main owns permission decisions and persistence. Production utility stdio is ignored; no environment text is added to debug logs or errors. Provider errors remain application-authored categories. These are trusted application boundaries, not an OS sandbox against malicious application code or hostile continuous ancestor-directory mutation. Provider-side retention after explicit external processing is outside Athena's local persistence guarantee.
